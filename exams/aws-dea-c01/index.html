At a FinTech payment processor building a real-time fraud detection lakehouse, the data engineering team must ingest streaming card transactions, compute 5-minute rolling velocity aggregates in real time, and land the enriched records as Apache Parquet files in Amazon S3 with the LEAST operational overhead. Select and order the 4 architectural steps from initial ingestion to S3 storage.

  1. A. Order 1 -> 2 -> 3 -> 4: (1) Ingest raw card events into Amazon Kinesis Data Streams -> (2) Process stateful 5-minute sliding windows using Amazon Managed Service for Apache Flink -> (3) Emit enriched aggregates to an Amazon Data Firehose delivery stream configured with inline Parquet conversion via a Glue Data Catalog table schema -> (4) Deliver the compressed Parquet partitions directly into the target Amazon S3 bucket.
  2. B. Order 2 -> 1 -> 4 -> 3: (1) Process windows in Flink -> (2) Ingest into Kinesis Data Streams -> (3) Write raw CSV to S3 -> (4) Run Data Firehose on S3 files.

  4. D. Order 3 -> 1 -> 2 -> 4: (1) Buffer in Data Firehose -> (2) Send to Kinesis Data Streams -> (3) Aggregate in Flink -> (4) Store in DynamoDB.

Sample Q2 · Domain 1: Data Ingestion and Transformation SINGLE-SELECT

An e-commerce marketplace ingesting millions of real-time clickstream and order events per hour has a data engineering squad that is currently captures website clickstream events. Three applications must each process every event within seconds, reading at their own pace. A fraud-model team plans to add a fourth application next month, and it must be able to start from the events captured earlier that same day. Which ingestion service should the data platform engineer use?

  1. A. An Amazon Data Firehose stream that delivers to Amazon S3.
  2. B. An Amazon SNS topic with an SQS queue for each application.
  3. C. An Amazon SQS standard queue shared by the applications.
  4. D. An Amazon Kinesis data stream in on-demand capacity mode.
Reveal Verified Answer (D), Technical Explanation & Exam Hack

Correct Answer: Option D

- **a** Firehose buffers and delivers records to a destination; it has no consumer API, so applications cannot each read the events within seconds, and the S3 copy arrives only after the buffer interval. - **b** SNS-to-SQS fan-out serves the three current applications, but SNS standard topics keep no history: a queue subscribed next month only receives events published after it subscribes. - **c** Consumers of one SQS queue compete for messages: each message goes to one consumer and is deleted after processing, so the applications would not each see every event. - **d** A Kinesis data stream retains records (24 hours by default) whether or not they were read, lets several consumers read the same records independently, and lets a new consumer start from TRIM_HORIZON or a timestamp to pick up earlier events. **The concept.** Kinesis Data Streams is a retained, multi-consumer stream; Firehose is delivery only, SQS is a competing-consumer queue, and SNS standard topics deliver only to current subscribers. **Why this is correct.** Two requirements decide it: every application reads every event independently, and a consumer added later must read events from earlier in the day. A Kinesis data stream keeps records for its retention period regardless of consumption, so any number of consumers read the same data at their own positions and a new one can start from the oldest retained record. SNS plus SQS meets the first requirement but not the second, a shared SQS queue meets neither, and Firehose exposes no read API at all. **How to reason it out** 1. Note the latency (seconds) and that every application needs every event. 2. Note the late-joining consumer: it needs events that were published before it existed. 3. Eliminate designs without retention a new reader can rewind into (SNS, SQS, Firehose). 4. Choose the retained multi-consumer stream: Kinesis Data Streams. > **Exam tip:** Many independent readers plus a late joiner that needs past events means a retained stream, not a queue, topic or delivery stream. Architectural Deep Dive: Amazon Kinesis Data Streams provides sub-second real-time stream ingestion with configurable retention (24 hours up to 365 days), replayability across multiple independent consumers, and optional Enhanced Fan-Out (2 MB/s dedicated throughput per consumer per shard via HTTP/2). Why Distractors Fail: Option A (An Amazon Data Firehose stream that delivers to Amazon S3....) is incorrect because that service applies to a different workload pattern and requires managing custom stream consumer infrastructure when the requirement is zero-administration delivery into S3, Redshift, or OpenSearch. Option B (An Amazon SNS topic with an SQS queue for each application....) is incorrect because that service applies to a different workload pattern and sets a short Visibility Timeout while the consumer takes several minutes to process messages (causing duplicate processing by other consumers) or uses Short Polling (WaitTimeSeconds=0) that burns money on empty API responses. Option C (An Amazon SQS standard queue shared by the applications....) is incorrect because that service applies to a different workload pattern and sets a short Visibility Timeout while the consumer takes several minutes to process messages (causing duplicate processing by other consumers) or uses Short Polling (WaitTimeSeconds=0) that burns money on empty API responses.

Production Use Case: High-velocity clickstream and payment fraud pipelines ingest events into Kinesis Data Streams in On-Demand mode (or Provisioned shards with 1 MB/s write and 2 MB/s read per shard) so Apache Flink, AWS Lambda, and Firehose can all read the exact same stream concurrently.
Exam Hack: Multiple consumers needing real-time replay + ordering per PartitionKey = Amazon Kinesis Data Streams. Use Enhanced Fan-Out when multiple consumers need dedicated 2 MB/s read bandwidth without throttling.
Sample Q3 · Domain 3: Data Operations and Support SINGLE-SELECT

At a connected-vehicle telemetry company streaming sensor payloads into AWS, the lead data architect is currently ingests article-view events into an Amazon Kinesis data stream. Traffic changes unpredictably from hour to hour, and the operations team does not want to forecast, monitor or adjust shard counts. Which configuration meets these requirements while minimizing ongoing operational maintenance?

  1. A. Switch the data stream to on-demand capacity mode.
  2. B. Replace the data stream with an Amazon MSK provisioned cluster.
  3. C. Keep provisioned mode with enough shards for the busiest hour.
  4. D. Keep provisioned mode and call UpdateShardCount from an alarm.
Reveal Verified Answer (A), Technical Explanation & Exam Hack

Correct Answer: Option A

- **a** On-demand mode manages shards for you and scales write and read capacity with observed traffic, so there is no shard count to forecast or adjust. - **b** An MSK provisioned cluster moves the capacity problem to brokers and partitions, adding operational work rather than removing it. - **c** Sizing for the peak still requires forecasting the peak and paying for idle shards the rest of the time, and an unforecast spike still throttles. - **d** Alarm-driven resharding works, but the team then owns the alarm thresholds, the scaling function and the UpdateShardCount quotas, which is exactly the capacity management they want to avoid. **The concept.** Kinesis Data Streams has two capacity modes: provisioned (you choose and change the shard count) and on-demand (AWS scales shards with traffic). **Why this is correct.** The deciding constraint is that nobody wants to plan or change capacity. On-demand mode removes shard management entirely. Alarm-driven UpdateShardCount and peak sizing both keep provisioned mode, so someone still forecasts or automates capacity, and MSK provisioned adds broker management. **How to reason it out** 1. Identify the workload: unpredictable traffic with no capacity planning wanted. 2. Compare provisioned options: both still require choosing or automating a shard count. 3. Pick the mode in which AWS manages shards: on-demand. > **Exam tip:** Unpredictable traffic and no shard management means Kinesis on-demand capacity mode. Why Distractors Fail: Option B (Replace the data stream with an Amazon MSK provisioned cluster....) is incorrect because that service applies to a different workload pattern and uses a non-replayable delivery buffer or competing queue where multiple independent consumers cannot replay historical stream records at their own pace. Option C (Keep provisioned mode with enough shards for the busiest hour....) is incorrect because that service applies to a different workload pattern and uses a non-replayable delivery buffer or competing queue where multiple independent consumers cannot replay historical stream records at their own pace. Option D (Keep provisioned mode and call UpdateShardCount from an alarm....) is incorrect because that service applies to a different workload pattern and uses a non-replayable delivery buffer or competing queue where multiple independent consumers cannot replay historical stream records at their own pace.

Sample Q4 · Domain 1: Data Ingestion and Transformation SINGLE-SELECT

[A capital markets risk-reporting organization running regulated analytics pipelines on AWS has a data engineer who] An on-premises Oracle database supports a live ordering system. A data engineer must copy the existing order rows into an Amazon S3 data lake and then keep S3 current with every insert, update and delete, while placing minimal load on the source. Which approach should the engineer use?

  1. A. An AWS DMS task of type full load and ongoing replication.
  2. B. An AWS DMS task of type CDC, started from the current time.
  3. C. A nightly AWS Glue JDBC job with bookmarks on the order ID.
  4. D. An AWS DMS task of type full load, rerun each night.
Reveal Verified Answer (A), Technical Explanation & Exam Hack

Correct Answer: Option A

- **a** Full load plus CDC copies the existing rows once and then reads the database transaction log to apply inserts, updates and deletes continuously, with little load on the source. - **b** A CDC task without a full load captures changes from its start point but never copies the rows that already exist, so the lake would be missing historical orders. - **c** A bookmark on a monotonically increasing key picks up new rows, but it never sees updates or deletes to existing rows, and nightly runs are not continuous. - **d** A nightly full load re-reads every table each time, which loads the source heavily and leaves S3 up to a day behind. **The concept.** AWS DMS tasks come in three types: full load (one-time copy), CDC only (changes from a start point) and full load plus CDC (copy, then continuous changes read from the transaction log). **Why this is correct.** The requirement has two halves: the existing rows and every later change, including deletes. Full load and ongoing replication covers both and reads changes from the redo log rather than by querying tables. Full load alone misses continuity and hammers the source, CDC only misses history, and a Glue JDBC bookmark sees only newly inserted keys. **How to reason it out** 1. Split the requirement: historical rows plus continuous inserts, updates and deletes. 2. Note that deletes and updates require log-based change capture, not key-based incremental reads. 3. Match both halves to one DMS task type: full load plus CDC. > **Exam tip:** Existing data plus every later change from a relational source means an AWS DMS full-load-and-CDC task. Architectural Deep Dive: AWS Database Migration Service (DMS) performs homogeneous and heterogeneous database migrations with minimal downtime using Full Load + Change Data Capture (CDC), while the AWS Schema Conversion Tool (SCT) converts heterogeneous database schemas, stored procedures, and views (for example, Oracle/SQL Server to Aurora PostgreSQL or Redshift). Why Distractors Fail: Option B (An AWS DMS task of type CDC, started from the current time....) is incorrect because that service applies to a different workload pattern and takes hours of production database downtime for a cold dump-and-restore or attempts heterogeneous schema conversion without AWS SCT. Option C (A nightly AWS Glue JDBC job with bookmarks on the order ID....) is incorrect because that service applies to a different workload pattern and re-scans the entire historical S3 bucket or table on every scheduled run, wasting DPU capacity and duplicating target records. Option D (An AWS DMS task of type full load, rerun each night....) is incorrect because that service applies to a different workload pattern and takes hours of production database downtime for a cold dump-and-restore or attempts heterogeneous schema conversion without AWS SCT.

Production Use Case: When migrating a 20 TB on-premises Oracle data warehouse to Amazon Redshift, engineers use AWS SCT Extraction Agents alongside DMS Full Load + CDC replication tasks.
Exam Hack: Minimal downtime live database migration / continuous CDC replication = AWS DMS. Heterogeneous engine schema & PL/SQL conversion = AWS SCT + DMS.
Sample Q5 · Domain 2: Data Store Management SINGLE-SELECT

[a multi-national logistics and supply-chain carrier tracking real-time shipment telemetry] Analysts use Amazon Athena to run monthly aggregate reports over the full history of a CSV data lake in Amazon S3. Each query reads 4 of the table's 120 columns across every row, and the Athena bill keeps rising. Which change reduces the data scanned per query by the LARGEST amount?

  1. A. Partition the CSV data in S3 by the year and month of each event.
  2. B. Move the CSV objects to the S3 Standard-Infrequent Access class.
  3. C. Compress the CSV files with gzip and keep the same table layout.
  4. D. Rewrite the data as Snappy-compressed Parquet with a Glue job.
Reveal Verified Answer (D), Technical Explanation & Exam Hack

Correct Answer: Option D

- **a** Partitioning prunes data only when queries filter on the partition columns. These reports aggregate the full history, so every partition is still read in full. - **b** A storage class changes the storage price, not the bytes Athena scans. Queries would scan the same data and also add retrieval charges. - **c** Athena bills on compressed bytes, so gzip does cut the scan, but every query still reads all 120 columns of every row. Columnar storage saves far more when queries touch 4 columns. - **d** Parquet is columnar, so Athena reads only the 4 referenced columns, and per-column compression shrinks those further. That attacks both the unused 116 columns and the raw size. **The concept.** Athena bills by bytes scanned. Row formats such as CSV force a query to read every column of every row; columnar formats such as Apache Parquet store each column separately so engines read only the referenced columns, and compress each column well. **Why this is correct.** Queries touching 4 of 120 columns waste roughly 97% of every CSV scan. Parquet removes that waste and adds compression on top, so it beats gzip CSV, which shrinks bytes but still reads every column. Partitioning is a strong lever only when queries filter on the partition key, and these full-history reports do not. Storage classes do not change scan volume at all. **How to reason it out** 1. Identify what Athena charges for: bytes scanned per query. 2. Note the access pattern: few columns, all rows, no selective filter. 3. Columnar layout removes unused columns from the scan; compression only shrinks what is still read. 4. Partitioning helps only with filters on the partition key, which these reports lack. > **Exam tip:** When queries read a few columns, columnar Parquet is the biggest scan-cost lever; partitioning helps only when queries filter on the partition key. Architectural Deep Dive: Amazon Athena is a serverless interactive query engine over S3 (charged at $5 per TB scanned): converting data to columnar Apache Parquet/ORC with Snappy compression, partitioning by high-frequency filter keys, and enabling Partition Projection (for highly predictable date/ID ranges without Glue Catalog metadata calls) cuts query latency and scan cost by up to 90-99%. Why Distractors Fail: Option A (Partition the CSV data in S3 by the year and month of each event....) is incorrect because that service applies to a different workload pattern and routes multi-gigabyte file uploads through a Lambda function or EC2 web tier instead of generating an S3 Pre-Signed URL for direct client-to-S3 upload, or forgets that S3 Pre-Signed URLs inherit the exact IAM permissions and session expiration of the principal that generated them. Option B (Move the CSV objects to the S3 Standard-Infrequent Access class....) is incorrect because that service applies to a different workload pattern and routes multi-gigabyte file uploads through a Lambda function or EC2 web tier instead of generating an S3 Pre-Signed URL for direct client-to-S3 upload, or forgets that S3 Pre-Signed URLs inherit the exact IAM permissions and session expiration of the principal that generated them. Option C (Compress the CSV files with gzip and keep the same table layout....) is incorrect because that service applies to a different workload pattern and writes hundreds of lines of raw CloudFormation boilerplate or attempts to run CodeDeploy EC2 shell scripts (`BeforeInstall`/`AfterInstall`) for serverless Lambda traffic shifting.

Production Use Case: To enforce FinOps cost guardrails across analyst teams, data engineers isolate teams into separate Athena Workgroups with 'Per-query data usage control' and 'Per-workgroup data usage alarms' in CloudWatch.
Exam Hack: Slash Athena cost & speed up queries = Parquet/ORC + Partitioning + Partition Projection (avoids MSCK REPAIR TABLE / Glue Crawler metadata bottleneck). Control analyst spend = Athena Workgroup data scan limits.
