Sample Q1 · Domain 2: Design Resilient Architectures SINGLE-SELECT

A global financial enterprise is updating its Disaster Recovery (DR) governance standards on AWS. The Chief Technology Officer asks the solutions architect to rank the four official AWS Disaster Recovery strategies in order from LOWEST cost (highest RTO/RPO) to HIGHEST availability (near-zero RTO/RPO): 1. Warm Standby (scaled-down but always-running functional copy of the production environment in a secondary Region). 2. Backup and Restore (periodic snapshots and data backups replicated to Amazon S3 in a secondary Region). 3. Multi-Site Active/Active (full-scale production capacity serving live traffic simultaneously across two or more Regions). 4. Pilot Light (core database replicated in real time to a secondary Region while compute instances remain stopped until failover). What is the correct sequence from lowest cost to lowest RTO/RPO?

  1. A. 2 -> 4 -> 1 -> 3
  2. B. 4 -> 2 -> 1 -> 3
  3. C. 2 -> 1 -> 4 -> 3
  4. D. 3 -> 1 -> 4 -> 2
Reveal Verified Answer (A), Technical Explanation & Exam Hack

Correct Answer: Option A

The AWS Disaster Recovery spectrum ordered from lowest cost / longest recovery time to highest cost / near-zero recovery time is: Backup and Restore (hours, 2) -> Pilot Light (tens of minutes, 4) -> Warm Standby (minutes, 1) -> Multi-Site Active/Active (real-time / seconds, 3). Architectural Deep Dive: For database resiliency and performance: Amazon RDS Multi-AZ provides synchronous standby replication for High Availability and automated failover (not read scaling), whereas Read Replicas use asynchronous replication to offload read-heavy reporting queries; Amazon Aurora provides 6-copy storage across 3 AZs, up to 15 low-latency Read Replicas, Aurora Serverless v2 for instant autoscaling, and Aurora Global Database for sub-second cross-region DR; Amazon DynamoDB delivers serverless single-digit millisecond NoSQL at any scale (accelerated to microseconds via DAX and replicated active-active worldwide via Global Tables); and Amazon ElastiCache for Redis provides sub-millisecond in-memory caching, sorted sets/leaderboards, and HIPAA-compliant encryption + Redis AUTH. Why the distractors fail: Option B is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario. Option C is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario. Option D is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario.

Production Use Case: High-traffic e-commerce platforms run Aurora PostgreSQL Multi-AZ for transactional writes, direct BI analytics to Read Replicas, cache hot product catalog queries in ElastiCache for Redis, and store shopping carts in DynamoDB.
Exam Hack: High Availability / Failover (synchronous) = RDS Multi-AZ. Offload heavy read traffic (asynchronous) = Read Replicas. Microsecond DynamoDB cache = DAX. Leaderboards / session state / sub-ms SQL cache = ElastiCache for Redis.
Sample Q2 · Domain 1: Design Secure Architectures SINGLE-SELECT

A company has a web application deployed on EC2 with an Application Load Balancer. The security team requires that all HTTP traffic be automatically redirected to HTTPS. What is the simplest solution?

  1. A. Configure a Security Group rule to block port 80
  2. B. Configure a listener rule on the ALB to redirect HTTP (port 80) to HTTPS (port 443)
  3. C. Use AWS WAF to block HTTP requests
  4. D. Modify the application code to detect HTTP and redirect to HTTPS
Reveal Verified Answer (B), Technical Explanation & Exam Hack

Correct Answer: Option B

The ALB natively supports listener rules that can redirect HTTP traffic to HTTPS with a 301 or 302 status code. This is the simplest and most efficient solution. Option A would block traffic instead of redirecting it. Option C is complex and unnecessary for a simple redirect. Option D requires code changes and is not the "simplest". Architectural Deep Dive: AWS Elastic Load Balancing offers three specialized load balancers: Application Load Balancer (ALB) operates at Layer 7 (HTTP/HTTPS/gRPC) supporting path/host routing, HTTP-to-HTTPS redirect rules, WebSockets, and Lambda/container targets; Network Load Balancer (NLB) operates at Layer 4 (TCP/UDP/TLS) handling millions of requests per second with ultra-low latency and static Elastic IPs per AZ; and Gateway Load Balancer (GWLB) operates at Layer 3 (GENEVE encapsulation on port 6081) to transparently insert third-party virtual network appliances (firewalls, IDS/IPS). Why the distractors fail: Option A is incorrect because this option routes high-volume S3/DynamoDB traffic through an expensive NAT Gateway, or tries to block a specific attacking IP address inside a Security Group (which only supports Allow rules). Option C is incorrect because this option embeds long-lived IAM User access keys or plaintext database passwords in code/environment variables instead of using IAM Roles and AWS Secrets Manager. Option D is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario.

Production Use Case: Enterprise web architectures place an ALB in public subnets with a native Listener Rule returning HTTP 301 redirects from port 80 to HTTPS port 443, forwarding traffic to private Auto Scaling EC2 or ECS Fargate targets.
Exam Hack: Layer 7 HTTP/HTTPS/Path/Host/Redirects = ALB. Layer 4 TCP/UDP + Static IP / Elastic IP + Extreme low latency = NLB. Third-party Firewall/IDS inline inspection = GWLB.
Sample Q3 · Domain 1: Design Secure Architectures SINGLE-SELECT

An enterprise financial organization is modernizing its cloud security posture on AWS to meet strict regulatory audit requirements. During an architecture review, the security engineering team evaluates access controls, encryption boundaries, and shared responsibility obligations. A company needs to give a Lambda application in Account A access to write to a DynamoDB table in Account B. What is the most secure way to implement this?

  1. A. Create an IAM user in Account B with access credentials and store them as environment variables in Lambda
  2. B. Create an IAM Role in Account B with DynamoDB permissions and configure a trust policy that allows Account A to assume the role
  3. C. Make the DynamoDB table public with a permissive resource policy
  4. D. Use VPC Peering between both accounts and access DynamoDB through the private network
Reveal Verified Answer (B), Technical Explanation & Exam Hack

Correct Answer: Option B

The cross-account pattern in AWS is implemented with IAM Roles and STS AssumeRole. A role is created in Account B with the necessary permissions and a trust policy that allows Account A (or a specific role) to assume that role. Lambda in Account A assumes the role and obtains temporary credentials. Option A uses long-term credentials (bad practice). Option C exposes data. Option D does not solve the IAM permissions problem. Architectural Deep Dive: For database resiliency and performance: Amazon RDS Multi-AZ provides synchronous standby replication for High Availability and automated failover (not read scaling), whereas Read Replicas use asynchronous replication to offload read-heavy reporting queries; Amazon Aurora provides 6-copy storage across 3 AZs, up to 15 low-latency Read Replicas, Aurora Serverless v2 for instant autoscaling, and Aurora Global Database for sub-second cross-region DR; Amazon DynamoDB delivers serverless single-digit millisecond NoSQL at any scale (accelerated to microseconds via DAX and replicated active-active worldwide via Global Tables); and Amazon ElastiCache for Redis provides sub-millisecond in-memory caching, sorted sets/leaderboards, and HIPAA-compliant encryption + Redis AUTH. Why the distractors fail: Option A is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario. Option C is incorrect because this option tries to use a synchronous Multi-AZ standby instance for read scaling, or uses an asynchronous Read Replica as a zero-data-loss HA failover mechanism. Option D is incorrect because this option tries to use a synchronous Multi-AZ standby instance for read scaling, or uses an asynchronous Read Replica as a zero-data-loss HA failover mechanism.

Production Use Case: High-traffic e-commerce platforms run Aurora PostgreSQL Multi-AZ for transactional writes, direct BI analytics to Read Replicas, cache hot product catalog queries in ElastiCache for Redis, and store shopping carts in DynamoDB.

Sample Q4 · Domain 1: Design Secure Architectures SINGLE-SELECT

A development team needs to store connection credentials for an RDS database. The credentials must be rotated automatically every 30 days without causing application downtime. What is the best solution?

  1. A. Store the credentials in a .env file in the application code and update them manually
  2. B. Store the credentials in AWS Systems Manager Parameter Store with manual rotation via Lambda
  3. C. Store the credentials in AWS Secrets Manager with automatic rotation enabled
  4. D. Store the encrypted credentials in S3 and read them when the application starts
Reveal Verified Answer (C), Technical Explanation & Exam Hack

Correct Answer: Option C

AWS Secrets Manager offers native automatic rotation for RDS, Aurora, Redshift, and DocumentDB database credentials. You just need to enable rotation and configure the period (30 days). Secrets Manager uses an AWS-managed Lambda to rotate credentials without downtime. Option B requires implementing rotation manually. Option A is insecure. Option D does not support automatic rotation. Architectural Deep Dive: For AWS security and compliance: IAM Roles with AWS STS AssumeRole provide short-lived temporary credentials for EC2, Lambda, and cross-account access (eliminating long-lived IAM User access keys); AWS Organizations Service Control Policies (SCPs) enforce central guardrails across member accounts; AWS KMS manages encryption keys (Customer Managed Keys / CMKs for custom rotation and cross-account access); AWS Secrets Manager stores and automatically rotates database credentials; AWS WAF protects ALB/CloudFront/API Gateway against Layer 7 SQLi/XSS and rate-based attacks; AWS Shield protects against DDoS; Amazon GuardDuty detects malicious account/VPC/S3 threat activity using ML; and Amazon Macie discovers sensitive PII in S3 buckets. Why the distractors fail: Option A is incorrect because this option introduces heavy operational overhead by managing custom scripts or raw compute instances when a fully managed AWS service solves the problem natively. Option B is incorrect because this option embeds long-lived IAM User access keys or plaintext database passwords in code/environment variables instead of using IAM Roles and AWS Secrets Manager. Option D is incorrect because this option either misapplies the AWS service outside its intended architectural pattern or violates the primary constraint (operational simplicity, cost efficiency, or target accuracy) specified in the scenario.

Production Use Case: Instead of creating static IAM user keys for a Lambda function in Account A to write to DynamoDB in Account B, architects create an IAM Role in Account B with a trust policy allowing Account A to call STS AssumeRole.
Exam Hack: Never pick static IAM User access keys! Always choose IAM Roles + STS AssumeRole for cross-account or compute permissions, AWS Secrets Manager for automated DB password rotation, AWS WAF for Layer 7 SQLi/XSS/IP rate limiting, and Amazon Macie for finding PII in S3.
Sample Q5 · Domain 1: Design Secure Architectures SINGLE-SELECT

A company has multiple AWS accounts under AWS Organizations. The security team wants to ensure that no account can launch EC2 instances outside the eu-west-1 and eu-central-1 regions. What is the correct approach?

  1. A. Create an IAM Policy in each account that denies EC2 actions outside those regions
  2. B. Create a Service Control Policy (SCP) on the OU that denies all EC2 actions if aws:RequestedRegion is not eu-west-1 or eu-central-1
  3. C. Configure AWS Config rules in each account to detect instances in non-permitted regions
  4. D. Use AWS Firewall Manager to block traffic from non-approved regions
Reveal Verified Answer (B), Technical Explanation & Exam Hack

An SCP with the `aws:RequestedRegion` condition can prevent any user or role (except the organization root) from launching resources outside the specified regions.
